# 客户演示原型主轴整改设计

## 目标与边界

本次将后台调整为“客户一眼能懂、能顺着办理”的交互原型。保留前端模拟数据，不新增数据库、真实支付、完整服务端权限或多人并发处理。但同一对象只能有一个维护入口，跨页面展示必须使用同一份前端状态。

## 信息架构

- 商品与权益：服务包、AI 加油包、机构额度入账、服务办理、服务权益、订单与流水。
- 内容管理：内容包、知识点、题目。学科、学段、年级和教材只作为筛选与归属维度。
- 学生管理：学生名单、服务权益、监护关系、微信重绑审核、学情概览与报告。
- 系统管理：基础主数据、AI 与用量规则、审计日志、异常处理。

## 唯一维护边界

1. 学科只在“系统管理 → 基础数据”新增、编辑和启停；内容管理删除学科 CRUD 和学科页。
2. 内容包只保留一套列表、新增流程和状态数据。
3. 授权码、家长绑定码和服务权益的办理由“商品与权益”拥有；学生管理仅展示结果和提供带上下文的跳转。
4. 机构额度的业务调整由“商品与权益”拥有；机构页只展示摘要并跳转。

## 核心演示流程

1. 用户在学生名单点击“办理服务”。
2. 系统进入商品与权益的办理面板，自动带入机构、教师和学生。
3. 用户选择服务包，页面清晰展示消耗点数、包含 AI 用量和有效期。
4. 确认后一次性生成学生授权码与家长绑定码，并创建一条待激活服务权益。
5. 成功结果页提供复制双码、继续办理和查看学生权益三个明确出口。
6. 回到学生管理后，同一学生立即显示待激活服务和双码结果。

## 数据与组件

- 在根级共享状态中维护学生、服务包、授权码、家长绑定码和派生服务权益。
- 建立纯函数 `createServiceFulfillment` 负责校验输入并返回双码与权益结果，方便自动测试。
- 建立可复用的学生摘要、服务包选择和办理结果组件。
- 基础数据选择继续使用现有 `MasterDataProvider`，内容页不再保留本地学科写入状态。

## 交互与异常状态

- 服务包停用、学生缺失机构或教师、点数不足时不能确认办理，并在面板内说明原因。
- 重复点击确认不得生成多套双码；按钮在处理中禁用。
- 所有成功操作使用页内结果和 toast，不使用阻塞式浏览器弹窗。
- 历史权益保留当时的服务包名称快照。

## 测试与验收

- 内容管理导航不出现“学科管理”和“新增学科”。
- 基础数据的启用学科仍可被知识点、题目和内容包表单使用。
- 从学生页发起办理时，机构、教师和学生不需要再次选择。
- 一次办理精确生成一个学生授权码、一个家长绑定码和一条待激活权益。
- 办理成功后，商品与权益和学生管理展示同一结果。
- 现有自动测试、类型检查和生产构建全部通过。

## 不在本次范围

- 真实后端持久化与 API。
- 真实点数批次冻结与消耗事务。
- 真实微信激活、短信、邮件或支付接口。
- 完整 RBAC 和租户服务端强制校验。
